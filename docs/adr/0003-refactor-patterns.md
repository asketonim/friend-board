# ADR 0003: Refactor patterns and component boundaries

Status: Accepted
Date: 2026-09-30

## Context

The fretboard refactor is being done in reviewable stages. During the work after ADR 0001 and ADR 0002, we made several implementation-pattern decisions that should guide future tasks.

This ADR records those patterns so future agents and contributors do not need to rediscover the same tradeoffs.

## Decision

Use small, explicit boundaries:

- container components own orchestration
- presentational components stay stateless and storage-agnostic
- URL-backed state is adapted at the page/container boundary
- cell-level UI uses a view model before rendering
- visual state maps to local class constants, not global styling abstractions by default

## Pattern 1: Commit accepted stages before starting the next stage

Refactors should be split into reviewable stages. Once a stage is accepted, commit it before starting the next one.

Rationale:

- Review diffs stay small.
- Reverts are scoped to one architectural move.
- Later stages do not blur whether a change belongs to an accepted decision or a new experiment.

Current sequence:

1. Extract presentational controls.
2. Move durable board-view state to URL search params.
3. Extract fretboard cell view model and cell component.
4. Add focused tests only if the extracted pure behavior warrants it.

## Pattern 2: Controlled presentational components emit domain changes

Presentational controls should receive values and emit domain-level changes. They should not know where state is stored.

Good shape:

```tsx
<ScaleControls
  scaleRoot={boardView.scaleRoot}
  scaleTypeId={boardView.scaleTypeId}
  showScale={boardView.showScale}
  onChange={replaceBoardView}
/>
```

Inside `ScaleControls`, emit patches like:

```ts
onChange({ scaleRoot: nextRoot })
onChange({ scaleTypeId: nextType })
onChange({ showScale: nextShowScale })
```

Avoid this inside presentational controls:

```ts
router.replace(...)
replaceParam("root", nextRoot)
```

Rationale:

- Controls remain reusable and testable.
- URL keys and routing behavior remain isolated.
- Storage can change later without changing controls.

## Pattern 3: URL-backed state exposes a domain patch updater, not raw query mutation

`useBoardViewSearchParams` should expose domain state and a domain patch function:

```ts
const { boardView, replaceBoardView } = useBoardViewSearchParams()
```

`replaceBoardView` accepts partial domain state:

```ts
replaceBoardView({ scaleRoot: "A" })
replaceBoardView({ showNoteLabels: false })
replaceBoardView({ scaleRoot: "F#", showScale: true })
```

It should not expose raw URL helpers such as:

```ts
replaceParam("root", "A")
replaceParams({ root: "A" })
```

Rationale:

- Raw query keys are implementation details.
- A patch updater supports multi-field changes with one URL replace.
- The container reads like product state, not routing plumbing.

Implementation requirements from ADR 0002 still apply:

- validate params
- fall back to defaults for invalid/missing values
- preserve unrelated query params
- use `router.replace`, not `router.push`
- keep microphone/live-detection state out of the URL

## Pattern 4: Isolate `useSearchParams` behind a Suspense-wrapped client subtree

When using Next App Router and `useSearchParams`, keep the route statically generated by moving URL-reading client logic into a child client component and wrapping it in `Suspense` from the server page.

Current shape:

```tsx
// src/app/page.tsx
import { Suspense } from "react"
import { Board } from "./Board"

export default function Home() {
  return (
    <Suspense>
      <Board />
    </Suspense>
  )
}
```

Rationale:

- This follows Next guidance for `useSearchParams`.
- It avoids a full client-side rendering bailout.
- It keeps the page shell statically generated.

Source: <https://nextjs.org/docs/messages/missing-suspense-with-csr-bailout>

## Pattern 5: Prefer cell view models for repeated grid/cell rendering

For repeated UI cells with non-trivial visual precedence, derive a small view model first, then render a presentational cell.

Current target shape:

```ts
export type FretboardCellModel = {
  key: string
  isOpenString: boolean
  noteName: NoteName | null
  pitchClass: number
  visualState: FretboardCellVisualState
}
```

The board component should stay focused on grid layout:

```tsx
const cell = getFretboardCellModel({
  position,
  detectedNotes,
  hasDetectedNote,
  showNoteLabels,
  scaleOverlay,
})

return <FretboardCell key={cell.key} cell={cell} stringStyle={stringStyle} />
```

Rationale:

- The render loop stops assembling partial boolean state.
- Cell visual precedence lives near cell rendering.
- Future `FretboardCell` changes are localized.
- The model gives a natural seam for optional focused tests.

## Pattern 6: Keep visual precedence explicit and local

Fretboard note visual precedence should be represented as named states:

```ts
export type FretboardCellVisualState =
  | "hidden"
  | "normal"
  | "dimmedByDetectedNote"
  | "scaleMuted"
  | "scaleMember"
  | "scaleRoot"
  | "detectedExact"
  | "detectedOutOfScale"
```

Current precedence:

1. hidden
2. detected out of active scale
3. exact detected note
4. scale root
5. scale member
6. scale muted
7. dimmed by another detected note
8. normal

Rationale:

- The names are easier to reason about than long boolean expressions.
- Future styling changes should map from state, not recompute state.
- A bug in precedence should be visible in one place.

## Pattern 7: Use `Record` for static visual-state class mapping

Use a static `Record<FretboardCellVisualState, string>` for visual-state class names.

Good shape:

```ts
const VISUAL_STATE_CLASS_NAMES: Record<FretboardCellVisualState, string> = {
  hidden: "opacity-0",
  normal: "opacity-100",
  scaleRoot: "...",
  detectedOutOfScale: "...",
  // every state must be present
}
```

Avoid `Map` for this case.

Rationale:

- Keys are a static string union.
- TypeScript enforces coverage for every visual state.
- `Record` is simpler and allocation-free compared with `new Map`.

## Pattern 8: Keep Tailwind abstractions local until reuse justifies global CSS/config

Do not introduce Tailwind config entries or global `@apply` classes for one component's evolving visual design.

Preferred order:

1. local constants in the component file
2. local semantic fragments if repeated inside the component
3. component-level CSS only if the component becomes unreadable
4. Tailwind config/global utilities only when styles are reused across components

Rationale:

- Global CSS/config is a design-system commitment.
- The fretboard visual language is still evolving.
- Keeping classes local makes state-to-style mapping easy to review.

## Pattern 9: Tests remain optional until the pure seam earns them

Do not add tests merely because a helper exists.

Add focused tests when they defend real behavior, for example:

- exact detected note beats scale member/root styling
- out-of-scale detected note beats normal exact styling
- scale active makes scale members visible
- labels off plus no scale hides non-detected notes

Avoid tests that assert:

- implementation wiring
- exact class strings without behavior value
- source text structure

Rationale:

- Refactor stages already use build/lint/browser smoke verification.
- Permanent tests should protect behavior, not freeze incidental implementation.

## Consequences

Future refactors should preserve these boundaries unless a new ADR supersedes them:

- presentational controls remain stateless and storage-agnostic
- URL state remains behind a domain adapter
- `Fretboard` remains board/grid focused
- `FretboardCell` owns cell model derivation and rendering
- styling stays local until reuse demands a broader abstraction
